# Readiness root cause recorded before behavior changes

Inspected Agent Control 9f0f9738ce79340dcef511786d481fc2b1cae4fc (4.5 base c50fcfa), native discovery types/adapters, CapabilityAdapterRegistry, external catalogue evaluator, and all 50 committed v0.1.0 manifests, specification and capability vocabulary at 0c72c8ca1cb897e100894babc2d1be437e4433f2.

1. Every manifest requires evidence.report. The evaluator receives an empty bindings map; it never derives capabilities. Even a supplied mapping needs HEALTHY, QUALIFIED/ACTIVE lifecycle AND operational state AND fresh AUTHORITATIVE provenance. Native successful local OS/GPU discovery emits DISCOVERED. Thus no capability matches; 50 UNSUPPORTED is an evaluator integration gap, not an estate capability finding.
2. assessReadiness unconditionally appends execution_grant_not_supplied for all jobs. The schema requires an explicit approval.required boolean, has no default, and the committed catalogue matches manifests. Exactly 8 true, 42 false. Output-write permission is universal, but scoped execution permission is different from consequential-action approval.
3. assessReadiness also unconditionally adds reviewed_job_adapter unless configuredJobs contains the job ID. This is not evidence of an operator configuration defect. Required target resources are also conflated with launch-time selection. All 50 require a scenario input; 25 declare a target resource (count verified in generated inspection).
4. Three connector declarations: discover-models/http, endpoint-health/http, home-entity-control/home-assistant. One credential: home-entity-control/home-assistant-token. Inbox triage consumes supplied synthetic messages; it does not declare email integration. Missing-credential is a synthetic failure scenario, not a live credential requirement.
5. Existing CapabilityAdapterRegistry governs adapter definitions (DRAFT through ENABLED), not capability proof. A version or endpoint probe does not prove arbitrary declared capabilities. Registered observations are CONFIGURED/DISCOVERED_UNQUALIFIED. Preserve this lifecycle and add derived evidence confidence separately; never promote adapter state or job qualification.
6. The old evaluator uses each job's 300-second result-evidence window for the entire estate. This is overly coarse for stable capability availability. A new projection will use bounded rule-specific capability TTLs, retaining result-evidence freshness as a launch/execution constraint. Failed or stale evidence cannot satisfy requirements.

Compatibility decision: keep the immutable v0.1.0 source and its reference launch-compatibility CLI unchanged. Add a versioned Agent Control technical-readiness projection, explicitly different from launch admission. Default v1 placement to one node; distributed placement requires an explicit digest-bound reviewed requirement contract. Input selection, authority, routing, execution integration and qualification are separate. Published capabilities are weakly specified and scenario-based: a declared-capability match is not proof of an arbitrary live business outcome.
